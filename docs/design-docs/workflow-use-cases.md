# Workflow 用例与构建顺序

**状态：** 初始切片实施中；以下是完整实现合同，不是全部已通过的测试。当前实现范围与限制见 [使用说明](../workflow-usage.md)。

本文约束 [Agent Workflows](agent-workflows.md) 的实现范围：以现有 Handoff、Advisor、Committee 三个真实场景驱动公共引擎，不先建设通用脚本平台。

研究依据：[调研 Paseo 内置 Skill 并翻译](codex://threads/01a0a7df-2e30-7a63-8560-967819ff7dc8)，2026-09-16；该调研固定 Paseo 源码为 `0eac75be7dd11a6623abb763b3a44d23e711c550`。本次读取调研及其本地分析文档，未重新运行 Paseo。基础 `paseo` Skill 是能力参考，不作为第四个 Workflow。调研建议的轻量 Skill 路线是另一种实现选择；本方案沿用已讨论的 Engine 路线。

## 用例决定能力

| 用例 | 核心问题 | 强制验证的公共能力 | 首次交付 |
|---|---|---|---|
| Handoff | 如何把明确的工作合同交给另一 Agent | 不可变材料、目标绑定、投递与确认分离、执行权边界 | 阶段 1 |
| Advisor | 如何征求意见而不转移任务责任 | 显式委派、结果合同、引用证据、有限追问 | 阶段 1 |
| Committee | 如何保留独立意见并处理分歧 | 相同输入版本、分支结果、有限互评、汇总与预算 | 阶段 2 串行；阶段 3 并行 |

每个用例都是内置计划构造器，输出相同的 plan transaction；Skill、CLI、UI 共用 Engine。首版不增加 YAML 解析器，不让三个场景分别持有运行状态、轮询器或结果存储。

场景预算在创建 Run 时冻结：Advisor 的 follow-up 最多一次，Committee 的 cross-review 最多一轮。内置计划构造器给步骤分配受校验的阶段与轮次，Engine 在 plan admission 中检查允许的阶段转移、角色数量及累计轮次；协调者不能通过改名或换 step ID 绕过。任意动态计划只有总预算保证，不宣称具有这些场景特定的轮数保证。该约束作为新增实现合同，尚未存在于当前协议。

## Handoff：材料交接与执行权交接

输入包括来源、目标 Profile、工作区、用户目标与禁止事项、briefing 或生成 briefing 的指令，以及原任务的完成标准。交接包保留已做工作、失败尝试、决策理由、实际验证、未提交状态、待确认项和下一步。

```text
briefing -> save-packet -> receiver-ack -> finish
                                          |
                           separate writer release / admission
```

已有 briefing 时直接引用经过校验的不可变输入，省略生成步骤。`--no-launch` 使用仅保存材料的变体；其结果明确为材料已保存，不声称接收方已接管。

`save-packet` 复用 Handoff 材料逻辑。接收方必须读取本次 packet，交付 packet digest、理解的任务边界、下一步和待澄清问题。确认仅证明对本次材料作出响应；关键问题未解决时由协调者追加 Human 步骤。不得把 pane 创建、idle 或屏幕中的完成语句当作确认。

材料交接成功不自动授权接收方写入。旧 writer 已停止或由用户核查处置后，才允许新 writer admission。Engine 的 reservation 仅约束受管理调度，不是操作系统文件锁。阶段 1 可通过收尾旧执行、新建后续 Run 完成这一边界，不要求实现阶段 3 的协调者迁移。

现有 `handoff save/to` 和 UI 保留入口，内部改为创建或驱动内置 Run。旧参数解析、放置策略、归档与提示生成尽量复用；取消与成功判断由 Engine 统一负责。兼容导出的 current 文件不作为历史 Run 的权威材料。

## Advisor：征求第二意见

输入包括明确问题、相关材料、已考虑方案与失败尝试、指定 Profile、访问约束和输出合同。输出必须包含建议、证据、风险、反对理由及待验证假设。

```text
question -> advisor-report -> coordinator-disposition -> finish
```

主 Agent 保留任务责任。协调者通过 claim-current 交付采纳/拒绝/待验证及理由，不向自己的 pane 注入指令。报告完整返回不代表建议正确，Run 成功不代表 WorkItem 完成。

第一轮报告必须被保存；追问创建新步骤并引用原报告，不覆盖旧交付。默认最多一次追问，Engine 同时限制本 Run 的总步骤、attempt 和时间预算。无法解决时保留未知项并结束，不隐式转成无限讨论。

顾问不获授源码写入能力。结果通过 Workflow delivery 提交，由应用保存 Artifact；这不要求顾问在仓库内创建报告文件。只读指令不等于沙箱：记录 executor 实际提供的限制；检测到工作区变化时标记证据版本变化，不能假装只读保证仍成立。转发 Skill 必须核对目标可用性和与只读合同的兼容性，冲突时报告 blocked。

## Committee：独立分析、有限互评、保留异议

默认两位成员读取同一冻结问题与证据版本。用户指定 Profile 优先；不同 Profile 不自动意味着不同模型或独立证据。无可用配置时明确报告缺口，不悄悄替换。

```text
question -> analysis-a --+
         -> analysis-b --+-> cross-review-a --+
                         -> cross-review-b --+-> synthesis -> finish
```

阶段 2 两份独立分析串行执行，均不得看到对方初始报告。阶段 3 保持相同结果合同，改为受控并行。相同工作目录、两个 pane 不足以保证上下文独立：需要新会话或可证明没有对方报告的上下文；做不到时显示限制，不声称独立分析。

默认最多一轮交叉质询。两份初始报告均接受后，才把双方报告交给互评步骤。协调者最后交付共识、分歧、各自证据、采用方案及理由、剩余未知项。达成共识不是成功条件；完整呈现未解决分歧可以是合格结果。

单个分支失败时保存其他交付，禁止假装全体意见已齐。显式人工决定可选择以部分结果结束，本 Run 标为 incomplete；输出同时列明缺席成员。达到轮次或总预算后不得靠新 step ID 继续讨论。

实施与实施后回审是后续独立用例，不属于 Committee 默认行为。Paseo 介绍页与 Skill 正文对此存在差异，不能将网页描述当作源码保证。

## 公共能力与边界

| 能力 | 被哪些用例使用 | 归属 |
|---|---|---|
| Profile 解析、目标准备 | 三者 | Agent Adapter，返回确定绑定与 generation |
| 工作区/材料版本采集 | 三者 | 注册原生能力或输入采集，输出不可变证据 |
| packet 创建与兼容导出 | Handoff | 原生 Action，复用已有材料逻辑 |
| Agent 执行、确认、交付 | 三者 | Agent Step 与 Attempt 协议 |
| 人工决定 | 三者异常路径 | Human Step，绑定具体材料摘要 |
| 依赖、join、预算、等待 | 三者 | Engine，不注册为模拟工作的 Action |
| 独立意见、互评、汇总 | Advisor / Committee | Agent 任务合同与 Skill，不写死为领域 Action |

三个场景共用 run snapshot、不可变 artifacts 和控制事件。事件至少关联 run、step、attempt、来源与单调 sequence。UI 在每个节点展示输入版本、最近可靠事实、等待原因、交付与下一步可用操作。Agent 自报、Adapter 观察和 Engine 接受分别展示来源。

## 场景验收矩阵

| ID | 阶段 | 测试输入或故障 | 必须满足 |
|---|---|---|---|
| HC-01 | 1 | 正常交接 | packet digest 对应明确接收确认；WorkItem 仍 active |
| HC-02 | 1 | 重复请求或目标启动失败 | 不重复建 Run；材料不丢失；失败不显示接管成功 |
| HC-03 | 1 | current 文件变化、旧 attempt 回包 | 本次材料不变；旧交付拒绝 |
| HC-04 | 1 | no-launch、旧 writer 未处理 | 前者仅报告材料保存；后者不授予新 writer |
| AC-01 | 1 | 顾问返回带风险的建议 | 保存完整报告及协调者处置，不转移任务责任 |
| AC-02 | 1 | idle、截断报告、重复 delivery | idle 不完成；无效报告不接受；重复提交幂等 |
| AC-03 | 1 | 一次追问后仍有未知项 | 保留两轮产物；预算阻止继续派发；未知项可见 |
| AC-04 | 1 | 所需 Skill 不可用或权限冲突 | blocked，有明确原因；不静默放宽能力 |
| CC-01 | 2 | 两位成员独立分析 | 同一输入版本；初始上下文不包含另一报告 |
| CC-02 | 2 | 互评后仍有分歧 | 最多一轮互评；汇总保留异议与证据 |
| CC-03 | 2 / 3 | 一位失败，另一位完成 | 保留成功产物；不提前 join；部分结束明确 incomplete |
| CC-04 | 2 / 3 | 分析期间输入代码变化 | 输出关联原版本；不作为新代码的验证证据 |
| CC-05 | 3 | 并行完成乱序与取消竞争 | 身份独立；取消后不派发汇总；迟到交付遵循 fence |
| CX-01 | 1 | 重启发生在投递后、确认前 | interrupted/unknown；不自动重发；历史可查看 |
| CX-02 | 1 | 结果落盘失败、UI 断线重连 | 不提前 ACK；重连从 snapshot/cursor 恢复视图 |

以上场景测试与主设计 WF-01 至 WF-20 共同验收。确定性 fake executor 用于故障注入；真实 Agent 测试验证终端投递与交付协议，两者不得混称。只读合规与报告语义质量另行评估，不能从状态机测试推断。

## 构建顺序与完成门槛

1. **公共最小内核**：计划校验、Step/Attempt/Delivery、持久化屏障、事件、取消与 interrupted。先以 fake executor 覆盖 CX 和相关 WF 测试。
2. **Handoff 纵向闭环**：接入现有材料服务与终端 Adapter，迁移 CLI/UI 入口并提供节点详情；通过 HC 和真实交接测试后再移除旧流程控制。
3. **Advisor 复用验证**：只增加任务合同、内置计划和场景 Skill；通过 AC。若必须新建独立状态机或结果仓库，应先修正公共边界。
4. **Committee 串行合同**：加入同输入独立分析、一轮互评和汇总，覆盖 CC-01 至 CC-04；保持总并发为 1。
5. **Committee 并行执行**：开放两个只读执行槽与 join，覆盖 CC-05；不同时引入并行写入、自动恢复或跨工作区集成。

每个切片都要具备 CLI 状态、可读运行记录和最小 UI 详情，不能把可观测性留到最后补。产品代码实现前为该切片列出具体文件、契约与测试命令；此文不表示实现已经开始或测试已经通过。
